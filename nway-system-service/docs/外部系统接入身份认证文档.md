# 外部系统接入 nway-system 身份认证文档

## 1. 概述

nway-system 提供两套面向外部系统的身份认证能力，可根据场景选择：

| 接入方式 | 适用场景 | 认证主体 | 说明 |
| --- | --- | --- | --- |
| **用户账号登录认证** | 子系统复用本系统的账号体系，代替用户完成登录 | 用户（工号 + 密码） | 返回用户 JWT，可调用业务接口 |
| **开放平台认证（推荐）** | 外部系统以应用身份访问本系统开放 API | 应用（appCode + appSecret） | OAuth2 风格，支持三种授权模式，配套 scope / 限流 / 白名单 / 审计 |

> 平台承载的微前端子应用（micro-app / wujie / iFrame）**不适用**上表的开放平台认证：宿主已注入用户 JWT，子应用只需对接登录态注入通道。两类接入形态的选择与接口边界见《[外部系统对接文档](外部系统对接文档.md)》第 1.1 节。

**基础信息**

- 服务地址：`http://<host>:8081`（端口可配置）
- 上下文路径：`/nway-system`（下文所有接口均基于该前缀）
- 统一响应格式：

```json
{
  "code": 200,        // 200 成功，非 200 失败
  "msg": null,        // 错误描述
  "data": {}          // 业务数据
}
```

## 2. 用户账号登录认证（JWT）

### 2.1 登录接口

```
POST /nway-system/login
Content-Type: application/json
```

请求体：

```json
{
  "name": "EMP001",          // 必填：用户名（工号）
  "key": "password123",      // 必填：密码（loginType=bio 时为指纹/面容标识）
  "clientType": "PC",        // 可选：客户端类型（PC/APP）
  "loginType": "password"    // 必填：password（账号密码）/ bio（指纹/面容）；旧值 external 兼容等同 password
}
```

> 账号密码的校验身份源（平台本地 / 外部统一身份认证）由服务端配置决定，调用方与登录页无感知，
> 详见 2.7。

响应（`data` 为 `LoginUser`）：

```json
{
  "code": 200,
  "msg": null,
  "data": {
    "employeeId": "EMP001",
    "token": "eyJhbGciOiJIUzI1NiJ9...",   // JWT，后续请求携带
    "realName": "张三",
    "avatar": null,
    "deptCodeList": ["D001"],
    "roleList": ["admin"],
    "tenantCode": "default",
    "tenantName": "默认租户",
    "superAdmin": false,
    "mainDeptId": "1",
    "mainDeptCode": "D001",
    "status": "using",
    "positionCodes": ["P001"],
    "tokenVersion": 0,
    "sessionId": "8f3a..."
  }
}
```

### 2.2 JWT 说明

| 属性 | 值 |
| --- | --- |
| 有效期 | 24 小时（可配置 `nway.jwt.expire-millis` / 环境变量 `JWT_EXPIRE_MILLIS`），空闲超过该时长需重新登录 |
| 签名算法 | HMAC-SHA256 |
| 签名密钥 | `nway.jwt.secret`（环境变量 `JWT_SECRET`，生产环境必须修改且 ≥ 32 字符） |
| 主要 Claims | `employeeId`（工号）、`tenantCode`（租户）、`superAdmin`、`roles`、`ver`（Token 版本号）、`sid`（会话标识）、`rc`（续期次数）、`exp`（过期时间） |

### 2.3 Token 使用规范

- 携带方式：请求头 `Authorization: Bearer <token>`（兼容不带 `Bearer ` 前缀的裸 Token）。
- **禁止**通过 URL Query 参数传递 Token。
- 服务端每次请求执行：本地 JWT 验签（不查 Redis）→ Token 版本号校验（强制下线 / 改密后旧 Token 立即失效）→ 接口级权限校验。
- Token 版本号机制：用户被强制下线或重置密码后，服务端自增版本号，所有旧 Token 失效（返回 401）。

### 2.4 登录安全策略

| 策略 | 规则 |
| --- | --- |
| IP 级限流 | 同一 IP 60 秒内最多 10 次登录尝试，超限拒绝 |
| 账号临时锁定 | 连续失败 5 次，锁定 30 分钟，到期自动解锁 |
| 账号永久禁用 | 仅管理员手动操作触发（登录时双重校验缓存与数据库状态） |
| 验证码 | Redis 存储，5 分钟有效，一次性使用 |

### 2.5 用户认证相关接口

| 接口 | 方法 | 说明 | 鉴权 |
| --- | --- | --- | --- |
| `/login` | POST | 登录认证，签发 JWT | 匿名 |
| `/login/getLoginUser` | GET | 获取当前登录用户信息（缺失/失效 Token 返回 HTTP 401） | 匿名路径，需携带有效 Token |
| `/login/refresh` | POST | Token 续期（见 2.6） | 匿名（Token 可选） |
| `/login/validateToken` | POST | 校验 Token 是否有效，返回 `{valid: true/false}` | 匿名（Token 可选） |
| `/login/logout` | POST | 登出，清除权限缓存与在线会话 | 需登录 |
| `/login/resetPassword` | POST | 重置当前用户密码 | 需登录 |
| `/login/external/changePassword` | POST | 外部账号自助改密（登录前密码已过期，需旧密码） | 匿名 |
| `/login/updateBioPc` / `/login/updateBioMobile` | POST | 绑定 PC / 移动端指纹面容标识 | 需登录 |

> 注意：`/login/getLoginUser`、`/login/refresh` 在 `url.anonymous` 中配置为匿名路径（不经过登录拦截器），但 `getLoginUser` 仍需在请求头携带 Token：无 Token/空白 → `HTTP 401`（body `code=401`，msg“未登录”）；过期/篡改/用户禁用 → `HTTP 401`（body `code=401`，msg“登录已失效，请重新登录”）；有效 Token → `HTTP 200` 返回用户信息。调用方统一按 HTTP 401 处理失效即可。

### 2.6 Token 续期机制

- 条件：旧 JWT **未过期**且**剩余时间不足 5 分钟**（可配置 `refresh-threshold-millis`）时才签发新 JWT；剩余充足时原样返回旧 Token。
- 限制：已过期 / 用户被禁用 / 版本号被撤销的 Token 不可续期；单个 Token 最大续期 **30 次**（24h × 30 ≈ 30 天会话上限），防止 Token 泄露后被无限续期。
- 已过期的 Token 无法续期，返回 `code=401`，需重新登录。

```
POST /nway-system/login/refresh
Authorization: Bearer <token>
→ 200 { "code": 200, "data": "<new-jwt>" }
```

### 2.7 账号密码身份源（本地 / 外部统一身份认证）

登录页只区分「账号密码」与「生物识别」两种方式；账号密码由谁校验对前端和对接方完全透明，
由 nway-system 服务端配置决定：

```
POST /login（loginType=password）
        │
        ▼
PasswordAuthorization（登录方式 password）
        │  nway.login.external.enabled ?
        ├─ 否 ──► LocalPasswordAuthenticator（平台本地 BCrypt）
        └─ 是 ──► ExternalPasswordAuthenticator ──► 外部系统 /portal/user/nwayLogin
                      │ 校验通过
                      ▼
                  ExternalUserProvisioner（租户校验 → 影子账号落地 → 登录态装配）
                      │
                      └─ 外部返回 1017（账号不存在）且 local-fallback=true → 回退本地 BCrypt
```

- `loginType=bio`（指纹/面容）始终校验平台本地生物识别凭证，与外部身份认证开关无关；
- 外部系统返回密码错误（1010）、服务不可用（1015）等**不降级**本地校验，避免绕过外部身份源安全策略；
- 身份校验与姓名/部门/岗位聚合由外部系统完成（OA 迁移期为 `nway-portal`，其把「OAM 换 token」替换为「AD 简单绑定」），nway 只落地影子账号并签发平台 JWT；
- 历史调用方仍可传 `loginType=external`，服务端按 `password` 处理，无需改造。

该能力默认关闭，开启需在 portal2 配置 `nway.auth.ad.*`（`AD_AUTH_ENABLED=true`、`AD_LDAP_URL`、`AD_BASE_DN` 等）
与 `nway.auth.token`，并在 nway-system 配置：

| 配置 | 说明 |
| --- | --- |
| `EXTERNAL_AUTH_ENABLED` | 是否启用外部认证（启用后所有 `loginType=password` 由外部系统校验；默认关闭） |
| `EXTERNAL_AUTH_BASE_URL` | 外部认证服务地址（含 context-path），如 `http://nway-portal2:8085/portal` |
| `EXTERNAL_AUTH_TOKEN` | 内部调用凭据，需与 portal2 的 `nway.auth.token` 一致 |
| `EXTERNAL_AUTH_TENANT_CODE` | 外部用户在 nway 的归属租户，默认 `default`（OA 迁移期配置为 `nway`） |
| `EXTERNAL_AUTH_AUTO_PROVISION` | 本地无账号时是否自动落地影子账号 |
| `EXTERNAL_AUTH_LOCAL_FALLBACK` | 外部账号不存在（code=1017）时是否回退平台本地密码认证 |

```
POST /nway-system/login
Content-Type: application/json

{ "name": "10086", "key": "******", "clientType": "PC", "loginType": "password" }

→ 200 { "code": 200, "data": { "employeeId": "10086", "token": "<nway-jwt>", "realName": "张三", ... } }
```

修改密码不在 nway-system 内实现：由 portal2 `/portal/user/nwayChangePassword` 承担
（AD `unicodePwd` + 复杂度校验），过渡期经 BFF 暴露。

外部系统失败时返回以下 code，由 nway 原样透传：

| code | 含义 |
| --- | --- |
| 1010 | AD 账号或密码错误 |
| 1011 | AD 账号已禁用 |
| 1012 | AD 账号已锁定 |
| 1013 | AD 密码已过期 |
| 1014 | 首次登录或密码已重置，需先改密 |
| 1015 | AD 服务不可用 |
| 1016 | AD 登录未配置或未启用 |
| 1017 | AD 中不存在该工号 |
| 1018 | AD 修改密码失败 |
| 1019 | 新密码不符合策略 |
| 1020 | OA 账号未落地且未开启自动补建 |
| 1021 | OA 租户未初始化 |

### 2.8 扩展新的登录方式（微信 / 企业微信等）

登录主流程按「登录方式」分发到 `AuthorizationService` 实现，新增登录方式不需要改动 `LoginService`：

1. 在 `LoginTypeEnum` 登记登录方式（如 `WEIXIN("weixin")`、`WECOM("wecom")`）；
2. 新增 `AuthorizationService` 实现并声明 `loginType()`：
   - 微信扫码/小程序：前端携带授权 code 调用 `/login`（`loginType=weixin`，`key=code`），服务端换取 openid/unionid；
   - 企业微信：`loginType=wecom`，`key=OAuth code`，服务端换取企业成员 userid；
3. 若身份由外部系统校验，复用 `ExternalUserProvisioner` 完成租户校验、影子账号落地与登录态装配；
   若需要先做账号绑定（openid/userid ↔ employeeId），在实现内完成绑定校验后再装配；
4. `AuthorizationServiceRegistry` 启动时自动收集全部实现并校验登录方式唯一性，重复注册会直接启动失败。

登录接口契约保持不变：新增方式仅扩展 `loginType` 取值与对应 `key` 语义，登录页按需增加入口即可。

## 3. 开放平台接入（OAuth2 风格，推荐外部系统使用）

### 3.1 前置条件：应用注册

1. 登录 nway-system 管理端，进入「系统管理 → 开放平台」。
2. 创建应用，填写应用编码（`appCode`）、应用名称，并配置：
   - **授权 Scope**：如 `user:read`、`org:read`、`msg:send` 等（详见 3.4）
   - **数据范围**（`dataScopeType`）：`ALL`（全部）/ `DEPT`（本部门）/ `DEPT_WITH_SUB`（本部门及子部门）/ `CUSTOM`（自定义部门）
   - **限流**：每秒请求上限、每日请求上限
   - **IP 白名单**：可访问的客户端 IP 列表（留空不限）
   - **有效期**：应用过期时间（留空永不过期）
3. 创建成功后系统**一次性返回明文 `appSecret`（64 位十六进制），请立即妥善保存**。数据库仅存 BCrypt 哈希，遗失只能重置。
4. 密钥重置：管理端「重置密钥」可生成新密钥，旧密钥立即失效。

### 3.2 获取 Token

```
POST /nway-system/open/token
Content-Type: application/x-www-form-urlencoded
```

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `appCode` | 是 | 应用编码 |
| `appSecret` | 是 | 应用密钥（明文） |
| `grantType` | 是 | `client_credentials` / `user_delegate` / `authorization_code` |
| `userToken` | 条件必填 | `user_delegate` 模式：已登录用户的 JWT |
| `code` | 条件必填 | `authorization_code` 模式：SSO 授权码 |
| `targetTenantCode` | 否 | `user_delegate` 模式：数据作用域租户，须 ∈ 代理用户可管理租户，缺省为应用所属租户；可管理租户通过 `GET /open/tenant/manageable` 查询 |

响应示例：

```json
{
  "code": 200,
  "msg": null,
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiJ9...",
    "token_type": "Bearer",
    "expires_in": 7200,          // 2 小时
    "scope": "user:read org:read",
    "employee_id": "EMP001"      // 仅 user_delegate / authorization_code 模式返回
  }
}
```

**三种授权模式对比**：

| 模式 | 用户上下文 | 典型场景 |
| --- | --- | --- |
| `client_credentials` | 无（应用身份） | 服务端到服务端的数据同步、批量查询 |
| `user_delegate` | 有（代理用户） | 外部系统已获得用户 JWT，代表该用户访问 |
| `authorization_code` | 有（SSO 用户） | 子系统 SSO 免登，用户在本系统完成认证后跳转 |

**Token 特性**：

- 开放平台 Token 使用**独立密钥**签名（`JWT_OPEN_SECRET`，未配置时降级用 `JWT_SECRET`），与用户 Token 完全隔离，互不通用。
- 有效期 **2 小时**，到期后需重新调用 `/open/token` 获取（无 refresh_token 机制）。
- Token 内嵌 `scope`、`dataScopeType`、`dataScopeDeptIds`、代理用户 `employeeId` 等信息，服务端每次请求从 Token 解析，无需回查应用配置。

### 3.3 调用开放 API

```
GET /nway-system/open/user/getByEmployeeId?employeeId=EMP001
Authorization: Bearer <access_token>
```

**请求链路校验**（由 OpenApiInterceptor 执行）：

1. Token 验签与类型校验（必须是开放平台 Token）
2. **Scope 校验**：从「路径 + HTTP 方法」推断所需 scope，Token 中 `grantedScopes` 须包含（或含通配 `*`），否则返回 403
3. **IP 白名单**：应用配置了白名单时，客户端 IP 必须在其中，否则返回 403
4. **限流**：超过应用每秒 / 每日上限返回 429
5. **数据范围过滤**（见 3.5）：`/open/*` 查询接口按应用数据范围 + 代理用户数据权限过滤返回结果
6. 设置应用上下文；若为代理用户模式，加载用户信息供数据范围过滤使用
7. 记录调用审计日志（应用、接口、参数、状态码、耗时、IP、代理用户）

**应用身份可信来源**：服务端一律从开放 Token（JWT subject）解析 `appCode`，**不信任任何请求头或请求参数中的应用标识**。早期版本部分接口依赖的 `X-App-Code` 请求头已废弃，请勿再传（传了也会被忽略）。

**开放 Token 不能**用于调用非 `/open/*` 的业务接口；用户 JWT 也不能用于调用 `/open/*` 接口（类型校验不通过）。

### 3.4 Scope 规则与开放接口清单

**Scope 推断规则**：

| HTTP 方法 | 所需 Scope |
| --- | --- |
| GET | `{module}:read`，如 `/open/user/*` → `user:read`，`/open/permission/*` → `permission:read` |
| POST（`/open/msg/*`） | `msg:send` |
| POST / PUT / PATCH / DELETE（其他模块） | `{module}:write` |

**当前开放接口**：

| 模块 | Scope | 接口 | 说明 |
| --- | --- | --- | --- |
| 用户 | `user:read` | `GET /open/user/getByEmployeeId` | 按工号查询用户基本信息（受数据范围约束，范围外用户返回 404） |
| 用户 | `user:read` | `GET /open/user/queryByDept` | 按部门查询用户列表（部门须在数据范围内） |
| 用户 | `user:write` | `POST /open/user/validateToken` | 验证用户 JWT 是否有效（POST 按规则推导为 `user:write`） |
| 组织 | `org:read` | `GET /open/org/deptTree` | 部门树（按数据范围过滤） |
| 组织 | `org:read` | `GET /open/org/positions` | 启用岗位列表 |
| 组织 | `org:read` | `GET /open/org/usersByPosition` | 按岗位查询用户（受数据范围约束） |
| 字典 | `dict:read` | `GET /open/dict/items?dictCode=xxx` | 按字典编码查询启用字典项 |
| 消息 | `msg:send` | `POST /open/msg/send` | 发送站内消息 |
| 权限策略 | `permission:read` | `GET /open/permission/policies?employeeId=` | 查询用户在**当前应用**（Token appCode）下的权限策略 |
| 权限策略 | `permission:read` | `GET /open/permission/check?employeeId=&resourceCode=&action=` | 快捷校验用户在当前应用下某资源的操作权限 |
| 菜单 | `menu:write` | `POST /open/menu/register` | 子应用全量注册/更新自身菜单（source=APP，不干扰平台菜单） |
| 菜单 | `menu:read` | `GET /open/menu/list` | 查询本应用已注册菜单 |
| 租户 | `tenant:read` | `GET /open/tenant/current` | 查询应用所属租户信息 |

> Scope 可在管理端随时调整，调整后**新签发的 Token 生效**，已签发的 Token 保持旧 scope 直至过期。
>
> 本表仅列出认证与权限相关接口；完整开放接口清单（含文件、低代码菜单、权限策略包、资源目录、租户可管理列表等）见《[外部系统对接文档](外部系统对接文档.md)》第 4 节。

### 3.5 数据范围过滤与配套 SDK

**两层数据范围取交集（更严者生效）**：

1. **应用数据范围**（`sys_open_app.data_scope_type`，管理端配置）：
   - `ALL`：不限制
   - `CUSTOM` / `DEPT` / `DEPT_WITH_SUB`：按配置的部门集合过滤（含子树展开）；应用身份无"本部门"概念，未配置部门集合时**拒绝返回数据**（fail-closed）
2. **代理用户数据权限**（`user_delegate` / `authorization_code` 模式）：取代理用户在平台（`nway-system:user` 资源）上的统一权限策略，语义与平台内部一致：`ALL` 不限制；`SELF` 仅本人；`DEPT` 主部门；`DEPT_WITH_SUB` 主部门及子树；`CUSTOM` 自定义部门集合；`EXPRESSION` 按主部门回退；无策略按 `SELF`（fail-closed）。

**配套 SDK（Java 微服务推荐）**：`nway-system-authz-sdk` 封装了策略拉取、本地缓存（1 分钟 TTL）、熔断 fail-closed、SQL WHERE 片段生成与 `@DataPermission` 注解 AOP。配置示例：

```yaml
nway:
  permission:
    platform-url: http://<host>:8081/nway-system
    app-code: order-system
    app-secret: <应用密钥>    # 推荐：SDK 自动获取并刷新 Token（过期前 5 分钟），401 自动重试
```

> 旧方式仅配 `app-token` 仍兼容，但 Token 2 小时过期后需自行更换，不推荐。

### 3.6 错误码

| code | 含义 | 说明 |
| --- | --- | --- |
| 200 | 成功 | — |
| 400 | 参数错误 | 参数缺失或格式错误 |
| 401 | 认证失败 | 应用不存在 / 已禁用 / 已过期 / 密钥错误 / Token 无效或过期 |
| 403 | 无权限 | 缺少所需 scope / IP 不在白名单 / 用户无接口访问权限 |
| 404 | 资源不存在 | 如用户不存在 |
| 429 | 请求过于频繁 | 触发每秒 / 每日限流 |
| 500 | 服务端错误 | 系统内部错误 |
| 1006 | 账号已锁定 | 登录时账号被禁用 |
| 1008 | 登录失败次数过多 | 触发临时锁定或 IP 限流 |

## 4. SSO 单点登录（authorization_code 模式）

适用于：外部子系统需要用户免登（用户在 nway-system 登录后，直接跳转子系统）。

**完整流程**：

```
┌─────────┐  1.用户已登录nway-system   ┌──────────────┐
│  nway-   │ ────────────────────────▶ │   子系统      │
│  system  │                           │  (外部系统)   │
└─────────┘                           └──────────────┘
    ▲  2.登录成功后调用                    │
    │     /login/sso/authorize           │
    │     生成一次性授权码 code            │
    │                                    3.302重定向
    │       ┌───────────────────────── redirectUri?code=xxx
    │       ▼
    │   ┌──────────────────┐
    │   │ 4.子系统用 code 调用 │
    └───│ POST /open/token  │
        │ grantType=        │
        │ authorization_code│
        └──────────────────┘
          5.返回 access_token（含 employee_id）
```

**步骤说明**：

1. 用户在 nway-system 完成登录。
2. 子系统前端调用授权码生成接口：

```
POST /nway-system/login/sso/authorize?appCode=<appCode>&redirectUri=<子系统回调地址>
Authorization: Bearer <用户JWT>
→ 200 { "code": 200, "data": { "code": "a1b2c3...", "redirectUri": "https://sub.example.com/callback" } }
```

3. 前端重定向到 `redirectUri?code=<授权码>`。
4. 子系统后端用授权码换取开放平台 Token（见 3.2，`grantType=authorization_code`），响应中 `employee_id` 即 SSO 用户工号。
5. 子系统基于 `employee_id` 建立本地会话，后续可用该开放 Token 调用 `/open/*` 接口。

**安全要点**：

- 授权码为 32 位十六进制随机串，Redis 存储，**5 分钟有效**，**一次性消费**（消费后立即删除，重复使用返回「授权码无效或已过期」）。
- 授权码**绑定 appCode**，换取 Token 时应用必须与生成授权码的应用一致。
- `redirectUri` 仅作为携带返回，子系统需自行校验回调地址与本地会话（防 CSRF），建议子系统保存随机 state 参数校验。

## 5. Webhook 事件回调

外部系统可订阅事件，本系统在事件发生时以 HTTP POST 异步推送。

**订阅方式**：管理端「开放平台 → Webhook」创建订阅，配置事件类型、回调 URL、HMAC 签名密钥（自行设置）、重试次数（默认 3）。

**支持的事件类型**：

| 事件 | 说明 |
| --- | --- |
| `user.created` | 用户创建 |
| `user.updated` | 用户信息变更 |
| `user.disabled` | 用户被禁用 |
| `dept.changed` | 部门变更 |
| `role.changed` | 角色变更 |
| `data_permission.changed` | 数据权限变更 |

**回调请求格式**：

```
POST <callbackUrl>
Content-Type: application/json
X-Webhook-Signature: <HMAC-SHA256 十六进制签名>
X-Webhook-Event: user.created
```

请求体：

```json
{
  "eventType": "user.created",
  "timestamp": 1724030000000,
  "data": { }
}
```

**签名验证（接收方必须执行）**：

- 算法：`HMAC-SHA256(secret, 原始请求体字符串)`，密钥为订阅时配置的 secret，结果以**十六进制小写**编码。
- 建议同时校验 `X-Webhook-Event` 与请求体 `eventType` 一致。

**重试策略**：回调非 2xx 或网络异常时重试，最多 `retryCount` 次（默认 3），指数退避（1s、2s、4s…），建议接收方接口幂等处理。

## 6. 配置项与环境变量

| 配置 | 环境变量 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `nway.jwt.secret` | `JWT_SECRET` | 内置默认值 | 用户 Token 签名密钥，**生产环境必须修改**（启动时校验：为空 / 不足 32 字符 / 生产环境使用默认值均拒绝启动） |
| `nway.jwt.open-secret` | `JWT_OPEN_SECRET` | 空 | 开放平台 Token 独立签名密钥，为空时降级使用 `secret` |
| `nway.jwt.expire-millis` | `JWT_EXPIRE_MILLIS` | 86400000（24 小时） | 用户 Token 有效期（空闲超过该时长需重新登录） |
| `nway.jwt.refresh-threshold-millis` | `JWT_REFRESH_THRESHOLD_MILLIS` | 300000（5 分钟） | 续期阈值 |
| `nway.jwt.max-refresh-count` | `JWT_MAX_REFRESH_COUNT` | 30 | 单 Token 最大续期次数 |
| `url.anonymous` | — | `/login` 等 | 匿名路径白名单 |

## 7. 接入清单与最佳实践

### 7.1 外部系统接入 Checklist

- [ ] 管理端创建开放平台应用，保存 `appCode` / `appSecret`，配置 scope、数据范围、限流、IP 白名单
- [ ] 服务端通过 `POST /open/token` 获取 Token，妥善保管（仅存服务端，勿下发浏览器）
- [ ] 调用 `/open/*` 接口时携带 `Authorization: Bearer <token>`
- [ ] Token 过期（2 小时）自动重新获取；对 401 / 403 / 429 错误做重试与告警
- [ ] 如做 SSO：接入 `/login/sso/authorize` + `authorization_code` 模式，回调地址校验防 CSRF
- [ ] 如订阅 Webhook：实现 HMAC-SHA256 签名验证、幂等处理、异步落库

### 7.2 安全最佳实践

1. **密钥安全**：`appSecret` 仅服务端持有；生产环境必须配置强 `JWT_SECRET`（≥32 字符随机串）与独立 `JWT_OPEN_SECRET`。
2. **最小权限**：按需申请 scope，避免授予 `*` 通配；数据范围优先选择 `DEPT` 而非 `ALL`。
3. **网络控制**：配置 IP 白名单 + 限流，Token 经 HTTPS 传输。
4. **令牌时效**：开放 Token 2 小时过期无刷新机制，需在服务端实现自动续期获取；用户 Token 续期依赖前端在有效期窗口内调用 `/login/refresh`。
5. **敏感操作**：改密 / 强制下线会使对应用户的全部 Token 立即失效（版本号机制），外部系统应捕获 401 后引导用户重新登录。
